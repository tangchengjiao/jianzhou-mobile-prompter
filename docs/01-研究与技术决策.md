# 研究与技术决策

研究日期：2026-10-26。范围：用户提供的桌面项目、可复用的开源移动提词器、系统官方文档、REA 官方仓库。当前为源码与资料研究，未连接手机；下文将事实、工程判断和待验证项分开。

## 1. 对这个产品的判断

可以做成适合个人长期使用的小工具。无需账户、会员、服务器或商业化系统。第一优先不是增加功能，而是让“打开稿子—调好阅读位置—在熟悉的拍摄 App 里开拍”顺畅。

用户补充后，产品的核心场景是 **跨 App 悬浮提词**，而非要求用户改用我们自己做的相机。由此，双端可以共享稿件格式、视觉和中文匹配规则，但不应假定悬浮和录音机制相同。

重要区别：

- 能显示在拍摄 App 上方，不等于该拍摄 App 录像时仍能听到麦克风。
- 能识别中文，不等于能正确跟上中文稿件中的重读、改口和跳段。
- 能在浏览器演示，不等于已经有可安装的原生手机应用。

iOS 的跨 App 画中画实验应成为第一项真机工作；若不满足用户用法，应及时说明，不用界面完善度掩盖能力不足。

## 2. 桌面项目究竟能复用什么

已获取并阅读 [jianzhou-canvas-recorder-build](https://github.com/tangchengjiao/jianzhou-canvas-recorder-build) 默认分支 `codex/macos-beta`，检查了真实提词组件、工程数据结构和手册截图。

| 已读模块 | 实际实现 | 移动端处理 |
| --- | --- | --- |
| `src/components/FloatingTeleprompter.tsx` | 本地保存稿件和参数、字号/透明度、播放和复位、拖动/缩放、精简阅读模式 | 复用交互经验和数据含义；移动布局重新设计 |
| 同文件的滚动逻辑 | `requestAnimationFrame` 按实际时间累计滚动，小数位置单独保存 | 借鉴“按时间移动、保持小数精度”；原生端改为原生时钟 |
| `src/core/courseProject.ts` | 提词状态含 text、scrollSpeed、opacity、position、size | 建立轻量稿件格式，并提供桌面导入适配 |
| `src/platform/hostBridge.ts` 等 | 桌面宿主能力单独封装 | 延续“能力由平台实现”的结构 |
| `src/styles.css`、手册截图 | 白底、深灰字、紫色强调 | 本次三张手机设计均以它为视觉基础 |

**不能直接移植的部分**：浏览器 DOM、textarea 滚动、桌面窗口置顶、画布/PDF/白板和录屏合成。Tauri 桌面的置顶行为不能用来证明手机可以跨应用悬浮。现有组件没有语音识别和稿件匹配，因此这两块需要新增。

桌面速度目前是像素/秒。手机显示“字/分”更容易理解，但不能只改标签：要依据真实字体、排版和可读字符数换算。调字号后应保留当前句子位置，再计算滚动距离。

源码入口：[FloatingTeleprompter.tsx](https://github.com/tangchengjiao/jianzhou-canvas-recorder-build/blob/codex/macos-beta/src/components/FloatingTeleprompter.tsx)、[courseProject.ts](https://github.com/tangchengjiao/jianzhou-canvas-recorder-build/blob/codex/macos-beta/src/core/courseProject.ts)。

## 3. 开源筛选结果

不按星数下结论。优先看源码里有没有目标能力，是否适合中文，以及能否在目标手机上验证。

| 项目 | 检查深度 | 可借鉴内容 | 当前缺口 | 选择 |
| --- | --- | --- | --- | --- |
| [Open Prompter](https://github.com/lelanddutcher/open-prompter) | 克隆并阅读 Swift 源码、测试目录、项目配置 | SwiftUI、语音后端接口、稿件偏置词、局部模糊定位、阅读位置和平滑追赶 | VoiceTracker 中仍有固定 `en-US`；分词偏英文，音近规则也是英文；iOS 工程目标 17+ | iOS 语音结构和滚动体验参考；不整体照搬 |
| [Reeb](https://github.com/aiwithenoch/reebopensource) | 克隆并阅读 PiP、语音、架构、安装文档与许可证 | 提词文字生成视频帧、画中画生命周期、同一次采集供录像和识别使用 | 稿件按空白分词；附带 tiny.en 英文模型；作者明确记录系统相机冲突；测试范围有限 | iOS 画中画和采集技术实验的首选参考 |
| [Suflyor](https://github.com/olerast67/voice-teleprompter-android) | 克隆并阅读 Android 清单、无障碍配置、音频采集、语言枚举、识别接口、说明 | 无障碍悬浮窗、跨 App 音频共享路径、离线流式引擎、稿件定位、遥控 | 目前只有 EN/RU，需要增加中文模型与规范化；作者说明约 130 MB，含两种模型；GPL-3.0 | 安卓首选研究基线；中文版本按实际需要裁剪 |
| [vass112/teleprompter](https://github.com/vass112/teleprompter) | 克隆，检查 manifest、工程与悬浮服务入口 | 简单 Kotlin 悬浮窗、播放控制、拖动与缩放 | 无语音识别；README 写 MIT，但未发现独立 LICENSE 正文；不要直接当成中文跟读成品 | 仅作普通悬浮交互对照 |
| [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/) | 官方移动端与流式模型文档 | Android / iOS 本地语音识别，已有中文流式模型 | 只提供语音能力，不负责全文定位、悬浮或双 App 抢麦问题 | 安卓中文语音候选引擎 |

Open Prompter、Reeb 均有 MIT 许可证正文。Suflyor 采用 GPL-3.0；个人自用可修改，若以后对外交付其派生版本，再按许可证处理对应源码和声明，不与闭源代码随意混装。这里不预先替用户决定将来的公开方式。

本轮不把英语/俄语支持描述为中文已支持，也不把维护者的机型测试描述为我们的测试。

## 4. 为什么中文需要重新处理

直接阅读源码发现：

- Reeb 使用 `script.split(whereSeparator: { $0.isWhitespace })`。中文长句没有空格，整句会成为一个“大词”。
- Open Prompter 按连续字母/数字构词，中文字符虽可能被识别为字母，但连续中文段仍未形成适合跟读的细粒度单位；其语音近似规则仅取 ASCII 字母。
- Suflyor 的 `SpeechLang` 当前只有 RU、EN，规范化和权重也按这两种语言分别处理。

因此“换成中文模型”只解决声音转文字，未解决稿件对应位置。我们的中文方案：以汉字粒度的稳定位置为基础，结合短语锚点；保留归一化字符到原稿位置的映射。数字、英文缩写、停顿、重复句是首轮重点，而不是一开始收集几十种罕见情况。

普通话优先。方言和夹杂英语先用本人实测判断是否需要优化，不预先承诺所有口音。

## 5. iPhone：可做的部分和必须实测的部分

苹果提供 [AVPictureInPictureController](https://developer.apple.com/documentation/avkit/avpictureinpicturecontroller) 及 sample-buffer 画中画内容源。把提词文本绘制成视频帧，是可研究的实现路径。

但这不是一个任意透明、任意按钮都可点击的悬浮 View。窗口大小、停靠位置、系统控制按钮有平台限制。设计图中的准备页可自由设计；实际 PiP 内部只能使用系统允许的能力，不把画在视频帧里的按钮伪装成可点击按钮。

**对系统相机**：Reeb 的 [架构记录](https://github.com/aiwithenoch/reebopensource/blob/main/ARCHITECTURE.md) 说明，原先的悬浮相机方案遭遇了后台音频中断及录像时麦克风独占。这是一个直接相关的负面样本，而非全机型结论；本项目也尚未实测。

**工程判断**：不应把“iPhone + 任意拍摄 App + 同时语音跟随”写成首版保证。先验证不占麦克风的匀速 PiP，再验证录像期间窗是否存活；有声音时才继续做跨 App 跟读实验。`mixWithOthers` 不是让其他 App 的录音输入自动共享给我们的开关。参考 [Apple 音频会话分类](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord)。

**对开拍、剪映**：必须分别测试具体版本，无法从系统相机或另一个 App 的表现推导。它们也不一定提供可从外部直接打开拍摄页的公开接口。首版“切换到拍摄 App”使用用户手动切换，不伪造一键跳转成功。

如跨 App 语音不可用，保留以下实际选择，不擅自替换用户的主流程：

1. 原拍摄 App + 可用的匀速 PiP，手动暂停/前后跳；窗口能否持续显示仍须真机通过。
2. 另一台手机显示并跟读，本机继续原 App 拍摄；硬件是否有待用户确认。
3. 用户愿意时，增加应用内原生拍摄：一次音频采集同时用于录像与识别。该方案可行性更明确，但改变拍摄流程，不能默认为已获偏好确认。

## 6. 安卓：普通悬浮与无障碍悬浮要区分

普通 `TYPE_APPLICATION_OVERLAY` 可以实现跨 App 浮层，需要“显示在其他应用上层”权限。然而，Android 官方 [音频输入共享规则](https://developer.android.com/media/platform/sharing-audio-input) 指出，两个普通 App 不能同时获得音频输入，拍摄 App 常用的音源还有较高优先级。

Suflyor 使用 `AccessibilityService` / `TYPE_ACCESSIBILITY_OVERLAY`，并将音频采集设置为非隐私敏感；这是官方文档覆盖的另一类共享场景，值得复用研究。它不需要读取聊天内容来实现提词。**但目标拍摄 App 的采集设置、系统版本与厂商实现仍会影响共享结果**，不能只因服务启动成功就宣布跟读成功。

建议安卓基线为 Android 10+；先选用户手边一台真机，验证前台录像有声、提词器也确实有识别结果，再完成中文接入。普通悬浮模式保留为匀速模式。不要用设置提示把用户导向一个实际不能跟读的状态。

系统 [SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer) 不保证设备上有中文离线服务，官方还提示其通用实现不面向持续识别。因此不把它当作国内安卓长时间口播的唯一引擎。

## 7. 技术路线比较

| 路线 | 优点 | 对本需求的代价 | 决策 |
| --- | --- | --- | --- |
| 手机网页/PWA | 安装最少、迭代快、适合演示界面 | 无法以网页模拟证明原生跨 App 浮层、后台音频和相机共存 | 只用于产品原型与独立阅读实验 |
| Flutter / React Native | 稿库和普通 UI 可以共享 | 关键 PiP、无障碍与音频仍须分别写原生模块；不自动省掉难点 | 如果后续稿库变复杂再评估，本轮不先加一层 |
| SwiftUI + Kotlin/Compose | 能直接借鉴两端原生项目，权限、生命周期和音频调试更直接 | 两套 UI 需维护 | 推荐本项目原生交付路线 |
| 整个桌面项目打包到手机 | 视觉和部分 TS 可复用 | 携带无关白板/PDF能力；桌面窗口与移动资源机制不一致 | 不选 |

共享的是稿件格式、设计规则、匹配规则和一组中文测试材料。先完成 iOS 体验；安卓的核心悬浮技术实验可以独立进行，不必等 iOS 功能全部完成。

## 8. 体积、耗电与语音模型

首版匀速悬浮不需要大模型。iOS 优先探测系统端侧识别能力；系统语言资产占用与应用安装包分开统计，不宣传为“零体积”。新系统的 [SpeechAnalyzer](https://developer.apple.com/videos/play/wwdc2025/277/) 可用于适配设备，旧系统走能力检测后的 SFSpeechRecognizer；不能仅凭系统大版本保证中文离线可用。

安卓先比较 sherpa-onnx 的中文小型流式模型，例如官方 [small online models](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/small-online-models.html) 列出的中文 int8 模型。按“跟读定位体验、持续速度、内存与发热”选型，不按转写榜单直接选最大模型。没有必要继承英文和俄文两套模型。

包体积必须用 Release 实包测：分别列安装包、安装后、首次语言资源、录制素材。当前没有本项目实包，不能报一个已经达到的 MB 数。目标是默认版本仅包含必要资源；需要独立模型时只提供中文一套，并允许单独导入模型。模型许可另行随选型核对。

跟读过程不用在线大语言模型。文字定位本身是小规模匹配问题，网络等待会增加拍摄时的不确定性。

## 9. 没有 Mac / 没有付费开发者账号怎么办

用户回答“没有”，当前暂按没有 Mac 和付费开发者账号规划；手机型号与 iOS 版本未确认，不推定用户没有 iPhone。

| 方式 | 是否需要买 Mac | 使用成本或维护 | 本项目如何使用 |
| --- | --- | --- | --- |
| 借用 Mac + Xcode 免费 Personal Team | 不必买，但构建/更新时需有可用 Mac | 苹果开发描述文件一般 7 天到期，需重装/刷新 | 可作首轮真机验证 |
| Windows + AltStore Classic | 手机安装可用 Windows | 免费签名仍需周期刷新；已有 IPA 也必须先用 Apple 工具链构建 | 可评估为早期自用路径，不会自动解决 Swift 编译 |
| 云端/借用 Mac 构建 + 付费开发者分发 | 不必拥有 Mac | Apple Developer Program 官方年费 99 美元或当地价格；证书/描述文件需维护 | 稳定长期使用时再决定，不现在代购或开通 |
| TestFlight | 可以云构建 | 需要开发者计划；每个构建可测试最多 90 天 | 对单人自用未必比直接设备安装省事 |
| Android APK | 不需要 Mac | 保留同一应用标识和签名以覆盖更新 | 直接交付 APK 与简明安装说明 |

来源：[Apple 免费团队限制](https://developer.apple.com/help/account/basics/about-your-developer-account)、[开发者计划](https://developer.apple.com/programs/)、[Ad Hoc 设备分发](https://developer.apple.com/help/account/devices/devices-overview)、[TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)、[AltStore Windows 安装](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows)、[AltStore 刷新](https://faq.altstore.io/altstore-classic/your-altstore)。

不要把苹果平台年费混同为我们的会员。我们可以不做会员，但无法承诺 iPhone 原生应用“永久免费安装且永远不用维护”。当前 Windows 环境可写 Swift 源码、做界面原型及安卓开发，不能直接本机运行 Xcode。

## 10. REA 在这个项目中的位置

用户提供的是 REA 截图。已核对官方来源为 [morluto/rea](https://github.com/morluto/rea)，包名 `rea-agents`，而不是搜索结果中的同名复刻。直接读取到的主分支 package.json 标为 6.8.0；截图为 6.4.0，故不按截图假定当前能力。

根据官方资料，当前 Android APK 静态分析可以配合 JADX 和完整 JDK 在 Windows x64 使用；Android 设备观察另需 adb，深度原生分析则依赖相应引擎。它能帮助查清 manifest、类调用、资源和运行行为，**不能改变系统麦克风权限或恢复所有原始源码**。

这轮已经有足够源码可读，暂未安装 REA、未修改 MCP 配置，也未逆向开拍/剪映。需要逆向的具体问题应写成可验证的问题，例如：“某安卓提词器依靠哪一种服务实现录像时继续识别？”随后使用用户已有且可分析的安装包，检查对应服务/调用并记录证据，再写自己的实现。现在没有目标 APK/IPA，不能声称做过逆向。

对本轮最有价值的是：先复用公开代码解释得清楚的能力；若仍有关键差异，再用 REA 研究那一小段行为。逆向结果也不能替代真实 iPhone 上的画中画兼容测试。

## 11. 下一步决策

界面已选择第三张，先将其做成完整操作原型。原生路线按上述方案准备；iOS 第一个有意义的里程碑是“在用户指定拍摄 App 真正录制时，提词窗还在、画面有声”。随后才谈跨 App 中文语音跟随是否能达到使用标准。
