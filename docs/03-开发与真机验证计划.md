## 3. iOS 先做一个小实验

参考 Reeb 的 PiP 文字帧链路，但首个版本不占用麦克风：

1. SwiftUI 稿件预览与参数页。
2. 将文字绘制成 sample buffer，交给 AVKit PiP。
3. 系统允许启动时再进入 PiP，处理正常关闭与恢复。
4. 使用系统允许的播放/暂停与跳转接口，检查实际按钮行为，不使用私有 API 隐藏控件。
5. 分别切到三个目标拍摄 App，区分打开、预览、真正开始录像三种状态。
6. 确认 PiP 是否继续显示和刷新，原视频声音是否完整，回到提词器是否可继续。

若 sample-buffer 刷新被后台策略影响，可比较预生成提词视频 + 原生播放器 PiP。这是另一条匀速方案，仍需相机录像中测试，不提前宣称可以规避中断。

跨 App 语音实验在“匀速浮窗可用”之后进行。不通过则记录限制，并保留经过验证的匀速能力；若用户坚持同时拥有语音跟随和原 App 拍摄，评估第二设备/协同方案，不擅自拿应用内相机顶替。

## 4. 双端语音结构

识别引擎与稿件匹配分离：

```text
稿件 → 归一化与位置映射 ───────────────┐
                                    ↓
音频输入 → 中文识别适配 → 最近识别片段 → 稿件定位 → 阅读位置控制 → 平滑显示
                                    ↑
                         点句重定位 / 暂停 / 重读
```

iOS：探测中文端侧能力，选可用的 SpeechAnalyzer 或 SFSpeechRecognizer 后端。没有离线中文资源时明确提示；不悄悄转到收费云接口。

Android：参考 Suflyor 的识别接口，接入一个中文流式模型；先比较小型 CTC / transducer 的实际跟读表现。无障碍悬浮场景与普通浮窗场景分别测试，避免丢掉音频后仍按估计速度冒充语音跟随。

定位输出至少包含：原文位置、是否可靠匹配、是否需要保持、建议移动目标。UI 不直接监听 ASR 文本就盲目跳动。

## 7. 安装与交付

iOS 免费试验路径：借用可用 Mac 进行构建，或用云端 Mac 产出合适的开发包，再评估 Windows 侧安装与周期刷新。免费签名的维护需要提前说清楚；不会要求用户把 Apple ID 密码发到聊天里。

若需要长期省维护，再讨论付费 Apple Developer Program、设备注册及 Ad Hoc 等安装方式；本轮不代付费、不注册账号。TestFlight 可选，但其构建有效期不能忽略。

Android 交付 APK，保留同一应用标识与发布签名，保证后续可覆盖更新。首次安装只说明实际需要的麦克风、悬浮或无障碍开关。仅匀速功能不申请麦克风。

## 8. 验证范围

原型：构建、页面无脚本错误、编辑重载保留、导入导出、空稿、参数更新、倒计时暂停、句子导航、浮窗拖动、iPhone/Pixel 布局。浏览器检查由用户明确同意，用本机浏览器与 Playwright 执行。
